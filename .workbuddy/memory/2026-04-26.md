## 移动APP扇区显示异常修复

### 问题描述
用户反馈：移动APP加载扇区后，所有站点扇区只显示一个方向的小区。

### 根因分析
后端 `/api/v1/map/data` 返回的数据结构为：
```json
{
  "sites": [
    {
      "id": "site_001",
      "name": "基站1",
      "latitude": 23.7,
      "longitude": 114.7,
      "networkType": "LTE",
      "sectors": [
        { "id": "s1", "azimuth": 0,   "pci": 10 },
        { "id": "s2", "azimuth": 120, "pci": 11 },
        { "id": "s3", "azimuth": 240, "pci": 12 }
      ]
    }
  ]
}
```

每个站点对象内含 `sectors` 数组，每个扇区有自己的 `azimuth`、`pci` 等属性。

但 `mobile-app/app/(tabs)/index.tsx` 中的 `loadSectors()` 函数错误地将 **站点对象** 直接当作 **扇区对象** 处理：
```typescript
const lte = sites
  .filter((s: any) => s.networkType === 'LTE')
  .map((s: any) => ({
    id: s.id || s.sectorId || Math.random().toString(36),
    azimuth: s.azimuth,  // 站点对象没有 azimuth，变为 undefined
    ...
  }));
```

后果：
1. 只渲染了站点数量个扇区（而非扇区总数）
2. 所有扇区的 `azimuth` 为 `undefined`，WebView 中 `sector.azimuth || 0` 全部回退到 `0`（正北方向）
3. 扇区名称、PCI、TAC 等也全部错误

### 修复内容

#### 1. `mobile-app/app/(tabs)/index.tsx` - `loadSectors()` 重写
- 遍历 `sites` 数组
- 对每个 `site`，展开其 `sectors` 数组
- 每个扇区使用自己的属性（`azimuth`、`pci`、`name` 等），缺失时回退到站点级属性
- 按 `networkType` 分别推入 `lte` / `nr` 数组

#### 2. `mobile-app/src/components/Map/MapView.tsx` - `updateSectors()` 增强
- 显式处理 `azimuth` 和 `beamwidth` 的 `undefined`/`null` 情况，避免隐式转换问题
- 统一 `sectorId` 变量，确保 `sectorOverlayMap` 映射键一致

#### 3. `calculateSectorPoints()` 方位角转换修复
- **根因**：原代码直接将地理方位角（0°=正北，顺时针）当作数学角度（0°=正东，逆时针）使用，导致扇区方向与方位角不一致
- **修复**：增加 `mathAngle = 90 - azimuth` 转换，并修正 `dx/dy` 的 `sin/cos` 使用
  - 地理方位角 0°（正北）→ 数学角度 90°（正北）
  - 地理方位角 90°（正东）→ 数学角度 0°（正东）
  - 地理方位角 180°（正南）→ 数学角度 -90°（正南）
  - 地理方位角 270°（正西）→ 数学角度 -180°（正西）

## 2026-04-26 追加修复：扇区ID唯一性问题

### 问题描述
用户再次反馈：扇区加载后，**同一站点仍只显示一个方向的扇区**。

### 根因分析
虽然 `loadSectors()` 已正确展开 `site.sectors`，但 **扇区ID生成逻辑存在缺陷**：
```typescript
id: sector.id || `${site.id}_${sector.sectorId || Math.random().toString(36)}`
```
当多个扇区的 `sector.id` 和 `sector.sectorId` 都缺失时，它们会生成相同的ID（因为 `Math.random()` 在同一事件循环中可能返回相同值，或者更常见的是——多个扇区都有相同的 `sectorId` 导致ID碰撞）。

在 WebView 的 `updateSectors()` 中，`sectorOverlayMap[sectorId]` 会被后续相同ID的扇区覆盖，导致最终每个站点只保留最后一个扇区的覆盖物。

### 修复内容

#### `mobile-app/app/(tabs)/index.tsx` - `loadSectors()` ID生成逻辑重构
```typescript
// 按方位角排序，确保同一站点的扇区顺序稳定
sectors.sort((a: any, b: any) => (a.azimuth ?? 0) - (b.azimuth ?? 0));

sectors.forEach((sector: any, sectorIndex: number) => {
  // 三级回退策略，确保ID绝对唯一
  const uniqueId = sector.id
    || (site.id && sector.sectorId ? `${site.id}_${sector.sectorId}` : null)
    || (site.id ? `${site.id}_idx${sectorIndex}` : `sector_${Math.random().toString(36).slice(2, 9)}`);
  ...
});
```
- **第一优先**：使用扇区自身的 `id`
- **第二优先**：组合 `site.id + sector.sectorId`
- **第三优先**：组合 `site.id + 数组索引`（确保同一站点内绝对唯一）
- **最终回退**：随机字符串（无站点ID时的兜底）

同时添加 `sectors.sort()` 按方位角排序，使同一站点的扇区渲染顺序稳定可预测。

### 修改文件
| 文件 | 改动 |
|---|---|
| `mobile-app/app/(tabs)/index.tsx` | `loadSectors()` 重构ID生成逻辑，添加扇区排序 |

### 根因分析

3. **降级为地图点击**：当 `getSectorsAtPoint` 返回空数组时，`handleTapInternal` 会降级发送 `mapClick` 消息，触发 `setSelectedLocation`，进而改变 `initialCenter` 导致地图移动

- 跳过水平边（`yj === yi`）避免除零错误
- 增加调试日志输出无效 path 的扇区ID

**2. `getSectorsAtPoint` 重构**（第 452-490 行）
- 新增 `getDistanceMeters` 辅助函数计算两点间距离
- 双策略检测：
  - **策略1**：精确的射线检测（多边形内 / 圆形内）

- 当精确检测失败时，返回距离最近的那个扇区

**3. `handleTapInternal` 日志增强**（第 146-185 行）
- 增加匹配到的扇区ID列表输出，便于调试

## 2026-04-26 第四次修复：点击扇区仍跳转地图问题

### 问题描述
点击扇区时仍然跳转到地图其他区域，没有显示扇区属性面板。

### 根因分析
经过深入排查，发现问题有多个层面：

1. **事件双重触发**：移动端 `touchend` 和 AMap 的 `click` 事件可能同时触发，导致 `handleTapInternal` 被调用两次
2. **去重机制缺陷**：原去重基于坐标字符串匹配（`lat.toFixed(5) + ',' + lng.toFixed(5)`），但两次事件的坐标可能有微小差异，导致去重失败
3. **扇区检测过于严格**：`pointInSector` 的射线检测对 60 米半径的小扇区过于严格，用户手指点击很容易落在扇区外
4. **多扇区重叠处理**：同一站点的多个扇区有重叠区域，用户点击时可能命中多个扇区，触发 `sectorOverlap` 而非 `sectorClick`

### 修复内容

#### `mobile-app/src/components/Map/MapView.tsx`

**1. `handleTapInternal` 去重机制重构**（第 146-189 行）
- 原逻辑：基于坐标字符串匹配去重
- 新逻辑：**纯时间-based 去重**，500ms 内的任何点击都直接跳过
- 简化扇区匹配处理：`getSectorsAtPoint` 已返回最匹配的单个扇区，直接发送 `sectorClick`

**2. `getSectorsAtPoint` 完全重构**（第 473-540 行）
- 新增 `getBearing` 函数：计算从扇区中心到点击点的方位角
- 新增 `azimuthDiff` 函数：计算两个方位角的最小差异（考虑 360° 环绕）
- 双策略检测：
  - 策略1：精确射线检测（多边形内 / 圆形内）
  - 策略2：容错检测 - 点击位置在扇区中心 **120 米** 范围内即命中
- 多扇区重叠时智能选择：
  - 室外扇区：选择方位角与点击方向最接近的
  - 室内扇区：选择距离最近的

**3. `pointInSector` 增强**（第 416-450 行）
- 增加 `path` 数组有效性检查（`Array.isArray`）
- 跳过水平边（`yj === yi`）避免除零错误

## 2026-04-26 第六次修复：点击扇区/地图跳转问题

### 问题描述
用户反馈：
1. **地点/小区搜索模式下**，点击扇区后地图跳转到很远区域
2. **坐标模式下**，点击扇区不会跳转
3. **关闭所有扇区图层后**，点击空白地图，地图会小幅度漂移

### 根因分析
经过分析，问题有两个层面：

**层面1：点击地图导致相机移动（所有模式通用）**
- `mobile-app/app/(tabs)/index.tsx` 中 `handleMapPress` 在非坐标模式下会调用 `setSelectedLocation({ lat, lng })`
- `MapView` 的 `initialCenter` 绑定了 `selectedLocation`，变化时触发 `moveCamera`
- 结果：点击地图任意位置都会移动相机到点击位置，造成"漂移"
- 坐标模式不调用 `setSelectedLocation`，所以不漂移

**层面2：点击扇区时 `mapClick` 被错误触发（搜索模式）**
- WebView 中同时存在 `touchend` DOM 事件和 AMap `map.on('click')` 事件
- 两者都会调用 `handleTapInternal` 进行扇区检测
- 如果 `map.on('click')` 先于 `touchend` 触发（AMap 内部事件合成顺序不确定），或 `touchend` 被 800ms 去重跳过
- `map.on('click')` 的 `getSectorsAtPoint` 可能因坐标微小差异返回空，降级发送 `mapClick`
- `mapClick` 触发 `handleMapPress` -> `setSelectedLocation` -> 相机移动
- 用户看到"跳转到很远的地方"（实际上是点击位置的坐标，但视觉上是从当前视图跳转）

### 修复内容

#### 1. `mobile-app/app/(tabs)/index.tsx` - 分离相机移动与位置选择
```typescript
// 修改前：
initialCenter={mapCenter || (selectedLocation ? [selectedLocation.lat, selectedLocation.lng] : undefined)}

// 修改后：
initialCenter={mapCenter}
```
- `initialCenter` 只接收 `mapCenter`
- 普通点击地图设置 `selectedLocation` 不再触发相机移动
- 只有搜索选择结果时 `setMapCenter()` 才会触发相机移动
- `NavControl` 仍由 `selectedLocation` 控制显示

#### 2. `mobile-app/src/components/Map/MapView.tsx` - 抑制移动端事件竞争
- 新增 `touchHandled` 标志变量
- `touchend` 处理点击前设置 `touchHandled = true`，800ms 后清除
- `map.on('click')` 中检查 `touchHandled`，如果为 `true` 则跳过处理，避免与 `touchend` 重复触发

#### 3. `mobile-app/src/components/Map/MapView.tsx` - 修复 `prevCenterRef` 状态残留
```typescript
useEffect(() => {
  if (!mapReady) return;
  if (!props.initialCenter) {
    prevCenterRef.current = null;  // 重置，避免下次相同坐标被跳过
    return;
  }
  // ...
}, [props.initialCenter, mapReady]);
```
- 当 `initialCenter` 变为 `undefined` 时重置 `prevCenterRef`
- 避免 `mapCenter` 重置后再设置为相同坐标时，被误判为"未变化"而跳过 `moveCamera`

| 文件 | 改动 |

## 2026-04-26 第七次修复：点击扇区不显示属性面板

### 问题描述
地图不再漂移，但点击扇区时不显示属性面板（Modal）。

### 根因分析
1. **touchend 点击判定阈值过严**：原阈值 15px/400ms 在移动设备上很容易因手指自然抖动被判定为"拖动"而非"点击"
2. **事件完全被吞掉**：touchend 被忽略后，即使 AMap 的 `map.on('click')` 触发，也可能因 `lastTapTime` 800ms 去重而被跳过，导致没有任何消息发送到 React Native
3. **touchHandled 抑制过于粗暴**：无论 touchend 是否检测到扇区都设置 `touchHandled`，导致 map.on('click') 完全失去兜底机会

### 修复内容

#### `mobile-app/src/components/Map/MapView.tsx`

**1. 放宽 touchend 点击阈值**
```javascript
// 修改前：
if (Math.abs(dx) > 15 || Math.abs(dy) > 15 || dt > 400) return;

// 修改后：
if (Math.abs(dx) > 40 || Math.abs(dy) > 40 || dt > 800) {
  log('touchend rejected: drag or long press');
  return;
}
```

**2. `handleTapInternal` 返回检测结果**
- 检测到扇区返回 `true`
- 未检测到返回 `false`
- 去重时间从 800ms 缩短到 300ms

**3. 智能抑制 `map.on('click')`**
```javascript
var detected = handleTapInternal(lnglat.getLat(), lnglat.getLng(), 'touchend');
if (detected) {
  touchHandled = true;
  setTimeout(function() { touchHandled = false; }, 300);
}
```
- 只有 touchend 成功检测到扇区时才抑制 map.on('click')
- 未检测到时不抑制，让 AMap click 用其内部坐标重新尝试检测

## 2026-04-26 第八次修复：WGS84 坐标系纠偏

### 问题描述
地图不漂移，但点击扇区仍不显示属性。用户提示：**扇区图层数据是 WGS84 坐标系**。

### 根因分析
高德地图（AMap）使用 **GCJ-02 坐标系**（国测局坐标），而后端返回的扇区数据是 **WGS84 坐标系**。两者在中国境内有 50~200 米的系统性偏移。

这导致两个层面的问题：
1. **显示层面**：直接将 WGS84 坐标传入 AMap，扇区覆盖物位置有偏移（虽然视觉上可能不明显）
2. **检测层面致命**：用户点击地图时，`e.lnglat` / `pixelToLngLat` 返回的是 **GCJ-02 坐标**，而 `sectorOverlayMap` 中存储的扇区中心是 **WGS84 坐标**。`getSectorsAtPoint` 用 GCJ-02 点击坐标去匹配 WGS84 扇区中心，计算出的距离就是 WGS84→GCJ-02 的偏移量（通常 > 60~120 米），远超扇区半径和容错距离，导致检测 **永远失败**。

### 修复内容

#### `mobile-app/src/components/Map/MapView.tsx`

**1. 内嵌 WGS84 -> GCJ-02 转换算法**
在 WebView JS 环境中增加标准的国测局偏移转换函数：
- `outOfChina`：境外坐标不转换
- `transformLat` / `transformLng`：偏移量计算
- `wgs84ToGcj02`：主转换函数

**2. `updateSectors` 创建覆盖物前转换坐标**
```javascript
var gcj = wgs84ToGcj02(sector.latitude, sector.longitude);
var gcjLat = gcj[0];
var gcjLng = gcj[1];

// Circle / Polygon 都使用 GCJ-02 坐标创建
overlay = new AMap.Circle({ center: [gcjLng, gcjLat], ... });
path = calculateSectorPoints(gcjLat, gcjLng, azimuth, beamwidth, 60);
```

**3. `sectorOverlayMap` 存储 GCJ-02 坐标**
```javascript
sectorOverlayMap[sectorId] = {
  overlay: overlay,
  data: sector,      // 原始 WGS84 数据（sectorClick 时发给 RN）
  gcjLat: gcjLat,    // GCJ-02 纬度
  gcjLng: gcjLng,    // GCJ-02 经度
  path: path         // GCJ-02 坐标的路径
};
```

**4. `pointInSector` 和 `getSectorsAtPoint` 使用 GCJ-02 检测**
- 边界检查、圆形距离、射线检测、容错距离、方位角匹配全部改用 `entry.gcjLat/gcjLng`
- 确保点击坐标（GCJ-02）和扇区坐标（GCJ-02）在同一坐标系下比较

#### `mobile-app/src/utils/coordinate.ts`
同步填充 RN 端的 WGS84↔GCJ-02 转换实现，供未来使用。

### 修改文件

## 2026-04-26 第九次修复：参考桌面端给覆盖物绑定 click 事件

### 问题描述
坐标系纠偏后，点击扇区仍不显示属性面板。

### 根因分析
桌面端（Leaflet）与移动端（AMap JS API）的事件机制差异：
- **桌面端**：Leaflet 给每个 `L.Polygon` / `L.CircleMarker` 直接绑定 `click` 事件，`e.stopPropagation()` 阻止冒泡，事件触发即拿到扇区数据
- **移动端**：之前完全依赖 `touchend` + `pixelToLngLat` + 自定义数学检测（射线检测/距离容错），中间环节越多越容易出错

即使坐标系已对齐，自定义的 `getSectorsAtPoint` 在移动端仍可能因以下原因失效：
1. `pixelToLngLat` 的像素坐标与 AMap Canvas 渲染的坐标存在微差
2. 手指触摸的 `clientX/clientY` 与 AMap 内部事件坐标不一致
3. 60米半径的扇区在屏幕上极小，容错距离 120 米仍可能不足

### 修复内容

#### `mobile-app/src/components/Map/MapView.tsx`

**给每个覆盖物绑定 AMap `click` 事件**
```javascript
(function(currentSector) {
  overlay.on('click', function(e) {
    if (e && e.stopPropagation) e.stopPropagation();
    var now = Date.now();
    if (now - lastTapTime < 300) return;
    lastTapTime = now;
    window.selectSector(currentSector.id);
    if (window.ReactNativeWebView) {
      window.ReactNativeWebView.postMessage(JSON.stringify({
        type: 'sectorClick', sector: currentSector
      }));
    }
  });
})(sector);
```
- 使用 IIFE 将当前 `sector` 绑定到闭包，避免循环变量共享问题
- `e.stopPropagation()` 阻止事件冒泡到地图
- 300ms 去重防止双击误触发

**保留原有兜底机制**
- `touchend` + `getSectorsAtPoint` 数学检测仍然保留，作为覆盖物 `click` 不可靠时的兜底

## 2026-04-26 第十次修复：测距完成按钮导致结束点漂移

### 问题描述

这个新点的坐标来自 AMap 对覆盖物点击位置的错误计算（或极小的 DOM 偏移被当成巨大坐标差），导致测量数组最后一个点变成异常值，视觉上"漂移到很远的地方"。

### 修复内容

#### `mobile-app/src/components/Map/MapView.tsx`

**1. 移除测距面板的 `clickable: false`**
```javascript
// 修改前：
clickable: false

// 修改后：
// 删除 clickable 属性（默认 true）
```
AMap Marker 默认 `clickable: true`，会拦截点击事件，阻止事件穿透到地图。

**2. 按钮 onclick 添加 `event.stopPropagation()`**
```javascript
panelHtml += '<button class="btn btn-finish" onclick="event.stopPropagation(); window.handleMeasureFinish()">完成</button>';
panelHtml += '<button class="btn btn-clear" onclick="event.stopPropagation(); window.handleMeasureClear()">清除</button>';
```

阻止 DOM 事件冒泡到 Marker 和地图。

**3. `handleMeasureFinish`/`handleMeasureClear` 设置抑制标志**
```javascript
var measureActionInProgress = false;

window.handleMeasureFinish = function() {

  setTimeout(function() { measureActionInProgress = false; }, 300);
  // ...
};
```

**4. `map.on('click')` 中检查抑制标志**
```javascript
map.on('click', function(e) {
  if (measureActionInProgress) {
    log('map.click suppressed (measure action in progress)');
    return;
  }
  // ...
});
```

三层防护（Marker 拦截 + DOM 阻止冒泡 + click 抑制标志），彻底杜绝按钮点击误触发地图 click。

## 2026-04-26 第十一次修复：touchend 坐标转换 API 错误

### 问题描述
测距点击"完成"后，结束点依然漂移到地图瓦片外很远的地方（截图显示 7147.14km）。

### 根因分析
**核心错误：`map.pixelToLngLat` 被误用于容器屏幕像素坐标。**

AMap JS API 中两个方法的区别：
- **`pixelToLngLat(pixel, zoom)`**：将**地图世界像素坐标**（基于当前缩放级别的世界地图像素，数值巨大，如 z16 时约 1600 万）转为经纬度
- **`containerToLngLat(pixel)`**：将**容器屏幕像素坐标**（相对于地图容器左上角的像素，如 200, 300）转为经纬度

代码中的 `touchend` 处理：
```javascript
var pixelX = touch.clientX - rect.left;  // 容器像素（0~屏幕宽）
var pixelY = touch.clientY - rect.top;   // 容器像素（0~屏幕高）
var lnglat = map.pixelToLngLat(new AMap.Pixel(pixelX, pixelY));  // 错误！
```

将容器像素坐标（如 200, 200）传入 `pixelToLngLat`，AMap 将其当成世界像素坐标处理，反算出的经纬度接近 **(-180°, 85°N)** 附近。从中国某点（如 113°E, 23°N）到这个异常点的 haversine 距离约为 **7147km**，与截图完全吻合。

**这同时也解释了之前多次修复中遇到的奇怪现象：**
1. **点击扇区检测不到**：`touchend` 用错误坐标做射线检测，永远命中不了扇区
2. **点击地图漂移**：`mapClick` 携带错误坐标，触发 `moveCamera` 飞到错误位置
3. **测距结束点飞到远处**：错误坐标被添加为测量点，导致巨大距离

### 修复内容

#### `mobile-app/src/components/Map/MapView.tsx`

**将 `pixelToLngLat` 改为 `containerToLngLat`**
```javascript
// 修改前：
var lnglat = map.pixelToLngLat(new AMap.Pixel(pixelX, pixelY));

// 修改后：
var lnglat = map.containerToLngLat(new AMap.Pixel(pixelX, pixelY));
```

`containerToLngLat` 是专门用于容器屏幕像素坐标转经纬度的 API，与 `touch.clientX - rect.left` 计算出的坐标系匹配。

### 修改文件
| 文件 | 改动 |
|---|---|
| `mobile-app/src/components/Map/MapView.tsx` | `touchend` 中将 `map.pixelToLngLat` 改为 `map.containerToLngLat` |

## 2026-04-26 第十二次修复：touchend 跳过 UI 覆盖物点击 + containerToLngLat 兜底

### 问题描述
用户通过 gsd-debug 反馈：测距结束点击"完成"后，结束点依然漂移到很远区域新建一个结束点。

### 根因分析
即使 `containerToLngLat` 已修正，用户点击测距面板的"完成"/"清除"按钮时，`touchend` 事件仍然会触发。`touchend` 会计算触摸位置的地图坐标并调用 `handleTapInternal`，如果未检测到扇区，会发送 `mapClick` 消息。

`mapClick` 如果在 `measureFinish` 之前被 React Native 处理，且此时 `measureMode` 闭包仍为 `true`，就会调用 `addMeasurePoint`，在按钮位置（最后一个测量点附近偏移 ~200m）添加一个新点。

虽然这个偏移只有约 200m，不会导致 7147km，但如果 `containerToLngLat` 在某些 AMap 版本中不可用，或者用户尚未重新加载最新代码，问题仍会表现为远距离漂移。

### 修复内容

#### `mobile-app/src/components/Map/MapView.tsx`

**1. `touchend` 中检测并跳过 UI 覆盖物点击**
```javascript
var target = e.target;
while (target) {
  if (target.classList && (
    target.classList.contains('measure-panel') ||
    target.classList.contains('measure-label') ||
    target.classList.contains('btn')
  )) {
    log('touchend skipped: UI overlay tap');
    touchStartPos = null;
    return;
  }
  target = target.parentElement;
}
```
- 当用户触摸测距面板、按钮或标签时，`touchend` 直接跳过，不发送任何 `mapClick`
- 这是最根本的防护：UI 元素的触摸不应被当成地图点击处理

**2. `containerToLngLat` 可用性检查 + 回退**
```javascript
var lnglat;
if (map.containerToLngLat) {
  lnglat = map.containerToLngLat(new AMap.Pixel(pixelX, pixelY));
} else {
  log('containerToLngLat not available, falling back to pixelToLngLat');
  lnglat = map.pixelToLngLat(new AMap.Pixel(pixelX, pixelY));
}
```
- 防御性编程：如果 `containerToLngLat` 不存在（某些 AMap 版本），记录日志并回退
